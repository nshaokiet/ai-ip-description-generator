## 1. Scope and decision boundary

Specify a local, disabled-by-default, synthetic-only contract that takes a **newly uploaded** PDF/DOCX through trusted intake, validated analysis and the existing offline P2-002…P2-006 stages. It must retain the actual validated APP-002 envelope before source cleanup, bind every later revision and output to that trusted intake, and permit Human review of a non-filing-ready draft. This is a proposal, not a frozen architecture, code change, browser API, security-policy approval, production Claims activation, real-paper permission or provider smoke authorization. Provider budget is USD 0. C2 implementation needs a separate decision after review and freeze.

The existing `CorePipelineOrchestrator.run_pipeline()` returns `PipelineResult(analysis,draft,metadata)` and deletes source in `finally`; it does **not** return the full `ExtractionInputEnvelope` ([core_pipeline.py](../../backend/app/services/core_pipeline.py)). The current v1 `/api/drafts/validate` and `/api/exports/docx` accept caller-supplied analysis/draft/revision and hash the supplied draft/revision, not a retained upload ([local_orchestration.py](../../backend/app/api/routes/local_orchestration.py)). A self-consistent foreign pair can therefore pass internal checks without proving custody of the uploaded source. C1 MUST NOT rebuild an envelope from analysis, treat a client-computed digest as authority, or silently reuse the fixed P2-007 demo fixture for a new upload.

## 3. Proposed trusted custody and data contracts

Recommend **Option A**, a trusted same-process atomic intake/extraction coordinator, for this local synthetic milestone. Its server-owned custody record T is created only while the APP-001 source lease is valid and before cleanup. It contains: random opaque `custody_id`; server owner/session scope; `document_id`; SHA-256 of the uploaded bytes from the registry and a fresh recheck; complete canonical `ExtractionInputEnvelope`; canonical envelope SHA-256; unique evidence-ID → (type, locator, content digest) index; canonical validated `structured_analysis` and digest; accepted P2-003/P2-004 configs and digests; revision number/token; monotonic deadline; lifecycle state; optional seven-original snapshot; and manifest. Sensitive originals remain private in memory. A record is not published until source identity, envelope, analysis schema/grounding and configuration admission all pass. Copy-on-commit under a per-session lock; if any step fails, erase candidate state and delete the upload. A process crash loses the volatile record and any unpublished output; startup/retry must reconcile and remove only service-owned staging paths. No database transaction or secure erase guarantee is asserted.

`CustodyReceipt` (proposed internal, path-free) exposes only opaque IDs, revision, state, source/envelope/analysis digests, evidence count and deadline class. It is **not** an authority to submit replacement originals. `TrustedRevision` binds custody ID + owner + source SHA-256 + envelope digest + analysis/config digests + seven current-original digests + revision. The opaque revision token is generated by trusted code; a changed original invalidates it. Raw SHA-256 and client-supplied token pairs are not authentication. Before every read/advance/revise/export, check owner, expiry, current revision and retained originals under the same lock. Duplicate concurrent operation keys either return the identical completed result for that exact revision or a safe conflict; no operation may reuse a stale result after revision change. Retry after uncertain crash rechecks actual committed state and never adopts a caller's package.

The trusted coordinator must verify `document_id` and file SHA-256 against the server registry/lease; compare envelope metadata and each source unit with that parsed source; run `validate_canonical_output` and `validate_grounding_and_business_rules` against **that envelope**; reject missing, repeated or foreign evidence IDs, wrong locators/excerpts, changed hash and noncanonical JSON. It then passes saved originals to `OfflineUSPTOOrchestrator.start_session()`. Its existing canonical digest checks protect retained contents against later changes, but are downstream integrity checks, not intake provenance proof. Foreign analysis/draft substitution remains rejected even if self-consistent and digest-valid.

### Seven-original provenance and revision rule

The exact `PROVENANCE_KEYS` in `uspto_offline_orchestration.py` are: `source_envelope`, `structured_analysis`, `reconstruction`, `specification`, `p2_003_generation_config`, `supported_claims`, `p2_004_generation_config`. Keep **all seven full originals**, not just hashes. At intake validate envelope and analysis against uploaded bytes; validate both configs with existing P2-003/P2-004 validators; validate each derived stage against retained upstream originals. At package and render, recheck canonical digest for each, verify same custody ID/source/revision, call `validate_uspto_document_package(package, **seven_originals)`, and pass all seven to `render_uspto_document_package`. Keep originals until downloads/expiry/abort finish; erase on cleanup. Source/analysis change invalidates P2-002 onward; P2-003 config change invalidates specification onward; P2-004 config change invalidates supported Claims onward. Any invalidation discards package, review approval and four-file manifest. Existing `revise_session` and `PROVENANCE_KEYS` are useful, but the new coordinator must prevent cross-upload replacement before calling them.

## 4. Lifecycle and failure contract

The following are **proposed C1 error codes**, not claims that current code emits them. All client-facing messages are fixed and source-safe; internal logs contain code, correlation/custody ID class and revision only. Every transition requires live owner scope, unexpired record, current revision token and retained upload binding. `ABORTED`/`EXPIRED` are terminal. TTL duration and retention require Human decision.

| Transition | Trusted input and invariant | Failure/code; filesystem and retry behavior |
|---|---|---|
| `NEW → INTAKE` | Local synthetic upload; APP-001 validates media/size and allocates ID | `SOURCE_REJECTED`; remove partial upload; same idempotency key may retry only if no committed record. |
| `INTAKE → SOURCE_VALIDATED` | Server rehashes leased bytes; APP-002 parses complete unique-ID envelope | `SOURCE_MISSING`, `SOURCE_HASH_MISMATCH`, `EVIDENCE_INVALID`; discard candidate, delete source. |
| `SOURCE_VALIDATED → ANALYSIS_VALIDATED` | Explicit synthetic extraction runtime; schema and grounding against saved envelope | `ANALYSIS_UNGROUNDED`, `PROVIDER_BLOCKED`; no session published, source cleanup. |
| `ANALYSIS_VALIDATED → CUSTODY_COMMITTED` | Atomic in-memory publication of T; retain envelope/analysis before upload deletion | `CUSTODY_COMMIT_FAILED`; no half record; cleanup failure is reported/recorded, not hidden. |
| `CUSTODY_COMMITTED → RECONSTRUCTED → SPECIFIED → CLAIMS_EVALUATED` | Current T and configs; P2-002/003/004 outputs and digests | `STAGE_REJECTED`; failed revision cannot advance; discard downstream, preserve only bounded diagnostic code. |
| `CLAIMS_EVALUATED → REVIEW_PENDING → REVIEW_RECORDED` | Human sees gaps/Claims status and current revision; explicit checkpoint records actor/time/decision **without legal approval** | `REVIEW_REQUIRED`, `STALE_REVISION`; unsupported/empty Claims never become positive. No finalized export before review. |
| `REVIEW_RECORDED → PACKAGE_VALID → RENDERING → RENDERED` | Seven originals verified, package reprojected; private staging; exactly four current-revision files | `PROVENANCE_MISMATCH`, `RENDER_INCOMPLETE`; do not advertise partial bundle; remove staging, keep session failed/retryable only by explicit safe policy. |
| `RENDERED → DOWNLOADED` | Owner/current revision/manifest entry; SHA-256 and size rechecked before each stream | `EXPORT_UNAVAILABLE`, `SESSION_UNAVAILABLE`; no arbitrary path; completion does not itself prove Human accepted legal content. |
| Any live state → `REVISED` | Trusted changed original, copy-on-write next revision and new token; review invalidated | `STALE_REVISION`, `REVISION_CONFLICT`; old outputs quarantined/removed; never serve old manifest. Retry only against observed new revision. |
| Any live state → `EXPIRED` / `ABORTED` | Deadline, explicit abort or fail-closed fatal error | Revoke access first; delete only recorded session-owned files and in-memory originals; report cleanup failure for later reconciliation. |

Concurrency: serialize transitions and manifest publication per custody ID; never hold a global lock while executing unbounded work. A second request using the old revision returns `STALE_REVISION`; an in-flight stage completing after revision/expiry must discard its result. Startup recovery scans only the configured private staging root with a service-owned marker and bounded age; do not delete unrecognized files. Existing `OfflineUSPTOOrchestrator` is process-local with `RLock` and no crash persistence; Option A therefore promises fail-closed loss on restart, not recovery of a draft. Explicit user retry creates a new trusted upload/custody record.

## 5. Trust, review and output boundary

Execution is local trusted caller only, opt-in and synthetic. No route is added. The Candidate A bearer is a same-process test capability, not browser authorization. A future browser API needs a separate Human decision for authentication, owner isolation, CSRF/CORS, bearer storage/transport, rate limits, retention, security review and deployment. Reject path-like IDs, symlink escapes, caller-selected output paths and arbitrary filesystem reads. Do not log source prose, prompts, tokens, credentials, bearer values, full hashes in public logs or private absolute paths. Audit events use safe IDs, stage/code, revision, timing and digest-verification verdict without raw source content. TTL, deletion assurance and backup/retention are unresolved Human policy gates; ordinary unlink is not assured secure deletion.

Human review must show missing information as missing, preserve `CLAIMS_REVIEW_REQUIRED` and `filing_ready=false`, and record the reviewed revision. `claims=[]` is not a positive Claims determination. Unsupported Claims remain absent; no patentability or filing decision is implied. P2-003's `claims_runtime_implemented=false` and current product Claims-disable boundary remain unchanged. Review is a content checkpoint, not legal approval.

The exact P2-006 filenames in `FILES` are `B2_REFERENCE_PREVIEW.pdf`, `B2_REFERENCE_PREVIEW.docx`, `USPTO_APPLICATION_DRAFT.pdf`, `USPTO_APPLICATION_DRAFT.docx`: two PDF/DOCX pairs. The manifest binds each fixed filename, MIME (`application/pdf` or DOCX MIME), size, SHA-256, custody ID and current revision. Derive from seven validated originals and current reviewed session only. Verify all four exist, signatures/size/hash, then atomically publish the bundle; downloads resolve a manifest key, never a user path, enforce owner/revision and `Cache-Control: no-store` in any future approved transport. On failure/expiry revoke first and clean staging/bundle. Package-only rendering, wrong-session download, stale revision, path traversal and partial bundles fail closed.

## 7. Architecture decision record — proposed, Human decision pending

| Criterion | A. Trusted same-process atomic coordinator (**recommended for synthetic milestone**) | B. Server-retained custody store with explicit expiry |
|---|---|---|
| Security / source identity | Server lease + rehash + envelope/analysis validation before in-memory commit; process-local owner scope | Same checks plus durable owner/tenant and store authorization, encryption/access policy required |
| Preservation / seven originals | Retain deep copies in bounded memory; loss on restart fails closed | Durable originals and recovery possible, but confidential retention/backup/deletion policy required |
| Complexity / compatibility | Small additive boundary around existing parser, validators and offline orchestrator; released v1 unchanged | Schema, migration, concurrency, backup and active-store safety work beyond current approval |
| Testability / rollback | Synthetic process tests; disable flag and discard ephemeral sessions | Storage integration and restore tests; rollback/data migration needs separate plan |
| Retention / production risk | Short volatile TTL proposed, no persistence or secure deletion claim | Greater data-retention and production migration risk |

Recommend A only for a **local synthetic proof**. Freeze requires Human to decide (1) whether C1 may create a new trusted coordinator and its precise owner model; (2) allowed synthetic data, TTL and cleanup-failure disposition; (3) Human review checkpoint semantics for non-final drafts; (4) whether four exports may be produced after `CLAIMS_REVIEW_REQUIRED`; and (5) whether any future browser transport is in scope (default: no). B or production persistence needs separate architecture/security authorization. Neither option proves paid model entitlement, semantic quality or filing readiness.
