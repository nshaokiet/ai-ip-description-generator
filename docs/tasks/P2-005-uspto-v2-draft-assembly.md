## 2. Objective and verified baseline

Provide a validated, deterministic, offline **assembly layer** that combines already-released source-grounded USPTO v2 disclosure and standalone supported Draft Claims into a **reviewable USPTO-style document package**. This is a prerequisite for the separately authorized DOCX v2 renderer (proposed P2-006) and real-paper E2E enablement (proposed P2-007, gated by security, funding and data permission).

Grounded baseline:
- P2-002: `INVENTION_RECONSTRUCTION` v1.0.0 generated by `reconstruct_invention(envelope, analysis)`.
- P2-003: deterministic `generate_uspto_specification(reconstruction, generation_config)` emits `USPTO_SPECIFICATION_DRAFT` v2.0.0, with Claims `MISSING`, `claims=[]`, `review_boundary.claims_runtime_implemented=false`.
- P2-004: `generate_supported_draft_claims(reconstruction, specification, generation_config)` emits a standalone `SUPPORTED_DRAFT_CLAIMS` v1.0.0; the component projection/handoff is specified by P2-004 §19.
- Current `POST /api/documents/{document_id}/process` returns analysis and draft v1; `POST /api/exports/docx` and `PatentDocxRenderer` consume v1. Neither route is a v2 assembly route.
- P2-001 v2.0.0 schema fixes `claims_runtime_implemented` to false; the released P2-003 exact-output validator depends on that contract.
- BLK-003 OPEN, EVAL-001 PRODUCT_RUNTIME deferred/awaiting funding, real/confidential input use not authorized; provider budget is zero.

## 3. Proposed architecture and scope

```text
APP-002 Evidence Envelope + AI-001 validated analysis [synthetic only]
     -> P2-002 validated reconstruction
     -> P2-003 validated USPTO v2 disclosure + exact generation-config sidecar
     -> P2-004 validated supported draft Claims + selected solution/config
     -> P2-005 offline integrity validator and pure assembly
     -> NEW versioned USPTO_DOCUMENT_PACKAGE (filing-style view + separate review sidecar)
     -> P2-006 DOCX v2 renderer [different task, NOT in P2-005]
```

P2-005 shall define a **new additive versioned package/schema** (proposed `USPTO_DOCUMENT_PACKAGE` v1.0.0) rather than silently edit, overwrite or rebrand P2-001 v2.0.0. P2-003's original output stays immutable with `claims_runtime_implemented=false` and Claims MISSING. Only a new assembled **document view** may contain projected supported Claims, and it must not masquerade as a P2-001-schema-valid runtime-true output. Preserve original P2-003 and P2-004 payloads (or immutable, content-addressed sidecars) for independent verification.

This draft proposes:
1. Exact typed input bundle: source evidence envelope, validated analysis, reconstructed invention, P2-003 draft, actual P2-003 generation-config sidecar, P2-004 standalone Claims and exact P2-004 config; explicit source-provenance assertion and selected solution are mandatory. The implementation may receive prevalidated upstream results from an internal orchestrator, but it must not trust an arbitrary caller's claim of validation.
2. Validate APP-002/AI-001 -> P2-002 projection at original boundary whenever the original inputs are supplied; re-run released P2-003/P2-004 validators or exact projection checks without weakening validation. No cross-document splicing, inferred sidecars, missing check shortcuts or reinterpreting raw paper inside the assembler.
3. Enforce equality of document_id/file name/media type and checksum **presence as well as value**, matching P2-004 source identity rules. Bind content hashes for full reconstruction, specification and Claims, not just superficial IDs. Explicitly reject stale/mismatched config, draft, provenance, selected solution or source.
4. Project P2-004 Claim/ClaimElement/ClaimSupport using **exact P2-004 §19 mapping**. Do not insert richer standalone audit fields into filing-facing Claims. Keep full support records, family structure, excluded candidates, warnings, missing information and author questions in a separate review sidecar.
5. If no supported Claims survive eligibility checks, preserve **no-Claims / HUMAN_CONFIRMATION_REQUIRED** semantics with nonempty missing-information linkage; never generate filler, fake Claims or mark Claims PRESENT.
6. If supported Claims survive, emit consecutive claim numbering, exact supported text and dependencies, Claims heading and preamble as specified in P2-004 §19; no unsupported broadening, auto-optimization, priority/inventorship strategy or unstated scientific technical effect.
7. Preserve P2-003 disclosed sections and Abstract unchanged. Maintain the canonical P2-001 section order in the filing-style view. Abstract must not exceed 150 words. Unsubstantiated administrative fields remain missing/confirmation-required; never invent inventors, assignee, application number, priority, publication or filing date.
8. Build separate structured `filing_view` vs `review_package`; keep internal provenance, support/evidence pointers, missing data and warnings out of filing-style paragraphs except explicit review markers permitted by a later renderer spec.
9. Deterministic canonical JSON, stable IDs/content digests, deep-copy/input nonmutation, side-effect-free validation and stable ordering. No implicit first/best solution and no nondeterministic provider output.
10. Fail closed with fixed safe diagnostic error codes/paths, without echoing confidential source excerpts into logs, exceptions or API errors.
11. Label **UNREVIEWED / draft only / requires qualified Human-IP review / filing_ready=false**. Success means schema/structural-source checks, **not** semantic entailment, legal completeness, patentability or USPTO acceptance.

## 6. Proposed test matrix

Positive:
- deterministic assembly of representative synthetic system/apparatus draft with eligible Claims;
- identical calls produce byte-equivalent canonical package IDs/ordering;
- faithful disclosure section order and Abstract; Claims numbered and with valid dependency/evidence links;
- faithful review sidecar retaining complete standalone support/issue provenance;
- supported zero-Claims case yields explicit review-required result, not false success;
- compatible synthetic variations of missing drawing/administrative sections do not fabricate content.

Negative / adversarial:
- document identity mismatch, checksum absent vs present, changed content under recycled ID, hash mismatch;
- stale P2-003 title-config sidecar or incorrect selected solution;
- mutated/speculatively upgraded Claim text, element, evidence reference or support status;
- fabricated claim dependency or cross-reference to nonexistent disclosure paragraph;
- unresolved conflict or unsupported source evidence; `INFERENCE`/`SAFE_GENERALIZATION`/unaudited Human states injected into P2-004 Claims;
- prompt injection inside source, metadata or supposed generation config;
- missing canonical Abstract or extra/reordered P2-001 sections;
- all source objects remain unchanged after successful or failed validation;
- protected v1 pipeline/exports and released P2-001…P2-004 schema bytes unaffected;
- no provider/network call, no real-paper test, no cost, no deployment.
